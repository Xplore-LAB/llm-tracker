# 账号系统后续开发方案

更新：2026-09-24。当前主线是 **GitHub Pages 双模式发布**：默认公开，管理员将 `TRACKER_AUTH_ENABLED` 设为 `true` 并重新部署后才启用 Supabase 登录。代码、本地测试和传统企业风格账号页面已完成，本次发布目标为公开模式，部署结果以 GitHub Actions 为准。实际操作与验收统一以 [Pages 接入手册](pages/README.md) 为准。独立服务器备选保留 [PocketBase 版本](README.md)，两套账号不互通。

## 第一阶段：先公开发布，再补齐登录环境

0. 先恢复 GitHub 发布授权、合入代码并将 Pages Source 设为 GitHub Actions；保持开关 `false` 发布公开版。此步骤不需要认证或邮件服务，账号功能预留在仓库中。
1. 用户持有的 Supabase 项目：安装 `pages/schema.sql`，关闭公开注册，配置邮箱密码规则、正式站点 URL 和回调。
2. SMTP 与发信域名：配置供应商、DNS、发件人，安装邀请/恢复模板。默认开发邮件不能覆盖团队成员。
3. 登录功能上线前：确认仓库写入和 Pages 管理权限，配置 3 个公开构建变量；真实账号/邮件验收准备完成后才把开关改为 true 并手动发布。公开模式无需这一步。
4. 两个真实测试邮箱完成接入手册全部验收，特别是跨浏览器邮件回调、停用已有会话、找回密码、自动更新后重新发布。

当前没有创建 SaaS 账号、购买域名或套餐、发送真实邀请、修改线上 Pages/Worker。公开模式不需要账号配置；登录模式缺配置时预览明确禁用登录、生产构建失败，不提供模拟账号兜底。关闭登录也必须重新部署公开产物，不能只停用工作流。

## 第二阶段：个人学习进度（尚未实现）

先盘点现有收藏、学习路径和已读记录的格式与稳定内容 ID，再定义最小 `learning_progress` 表：

| 字段 | 用途 |
| --- | --- |
| `user_id` | 关联 Auth 用户，和 `item_type` / `item_id` 组成唯一键 |
| `item_type` / `item_id` | 区分论文、课程/路径节点，不用易变标题作 ID |
| `state` | 未开始/进行中/已完成，约束合法值 |
| `position` 或 `progress` | 按内容类型确定，有范围限制 |
| `updated_at` / `version` | 服务器时间与乐观并发，处理多设备冲突 |

RLS 的 SELECT/INSERT/UPDATE/DELETE 都必须同时要求 `auth.uid() = user_id` 和 `tracker_members.status = 'active'`；UPDATE 的 USING 与 WITH CHECK 都要限制，禁止转移记录归属。服务端约束 item 类型和进度取值。不得只依赖前端过滤，也不得把 `service_role` 放浏览器。先做两个真实成员的双向越权测试，再加页面。

浏览器记录导入需成员明确确认，不能把共享浏览器的旧匿名记录自动判给当前账号。保存失败要有可见提示和重试；离线变更、删除同步、多设备冲突要有明确规则。进度页仅展示当前成员；管理员统计访问另行确定，不因管理员能管账号就默认展示全部个人学习内容。

验收：A/B 数据隔离；A 不能写 B 的 ID；停用后旧 token 的数据读写也失败；清理本地缓存后云记录可恢复；并发更新不静默覆盖；导入可去重；删除账号的数据保留策略有记录。

## 第三阶段：真正保护网页和数据

用户已接受当前公开 Pages 内容仍可直接读取。若以后要求“未登录不能拿到 HTML/JSON”，迁出静态公开托管，加服务端网关：

**优先保留 Supabase 身份**：服务器验证会话和成员资格，再返回静态文件/私有数据，减少已有账号和进度迁移。可将前端部署与后端统一域名，设计安全会话 Cookie、CSRF、缓存和请求限流。账号平台可以继续托管，或评估自托管成本。

**备选使用已实现的 PocketBase 包装**：一台带持久磁盘的 Linux 主机、HTTPS 域名、PocketBase 和备份。访问控制与后台已通过本地真实服务测试，但它是另一套身份；需明确 Auth 用户 ID 到 PB members ID 的映射、重新邀请/设密以及进度迁移，不能承诺旧密码自动兼容。

切换清单：确定域名与主机 → 配置 HTTPS/代理/备份 → 新站测试 → 验证停用与恢复 → 切换入口 → 按授权范围关闭旧公开 Pages/Worker/静态旁路 → 保留回退方案。公开仓库及已下载文件不会随新服务器上线变私密。不在本阶段关闭现有入口。

## 日常运维与后续能力

- 确定一名主要管理员和恢复联系人，不共享管理员密码；备份平台恢复方式。成员 MFA、CAPTCHA、密码重新认证 OTP 未接入页面，启用前完成对应流程。
- 免费项目可能暂停；上线后记录唤醒方法、依赖服务故障时的联系渠道和费用阈值，不靠绕过平台限制保持活跃。
- 定期导出成员资格和未来进度；备份能力按实际套餐确认，演练恢复。SMTP 密钥和平台管理密钥只存后台/秘密管理系统。
- 依赖固定版本，升级先跑现有测试；保留构建版本号和上线验收记录。管理员操作审计依赖平台日志的实际保留期，长期审计后续另做。
- 如开放自助邮箱注册，新增验证类型/注册页面、审核与反滥用、邮箱重复处理、隐私说明；当前邀请制不需要开放注册。
- 可用性提升按真实需求追加，不在小团队阶段重做账号平台、增加复杂角色树或自建发信系统。
